# B 发起诊断任务并交付给 D

本阶段实现 B 的任务创建、持久化、输入冻结、通知投递、失败重试与权限查询。正常提交和超时结算在保存成绩的同一事务中创建任务；独立 worker 在事务提交后向 D 发送 task_id 和 attempt_id，D 再从 B 获取冻结诊断输入。

**delivered 表示 D 已持久化接收任务，不表示已生成诊断报告。** 本阶段没有增加 D 的算法、诊断完成回调、报告保存或学生报告页面。

当前仓库中的 D 仍只有 `POST /internal/diagnose-and-recommend`，它接收完整的旧版评分数据，不能接收本通知。D 成员需要实现本文第 5 节的接收契约；B 已完成调用方并用 HTTP 替身验证。未适配前，向现有 D 投递会收到 404，任务标为 failed，不伪装成诊断成功。本次未修改 C/D 项目。

## 1. 运行前准备

1. 更新 B 后，按实际数据库名执行 [create_diagnosis_tasks.sql](../sql/create_diagnosis_tasks.sql)，或者重启由 create_all 创建缺失表。已有数据库仍需按以前的迁移说明确保 resource_index_states 等表完整。脚本不修改旧表、不批量生成历史任务；DDL 隐式提交。
2. 在 `.env` 配置以下变量，重启 B。密钥分别运行 `python -c 'import secrets; print(secrets.token_hex(32))'` 生成，不写入仓库。

```dotenv
DIAGNOSIS_AUTO_ENQUEUE=true
DIAGNOSIS_URL=http://127.0.0.1:8002
DIAGNOSIS_SERVICE_KEY=填写B调用D的独立随机密钥
DIAGNOSIS_TIMEOUT=10
DIAGNOSIS_MAX_ATTEMPTS=5

D_SERVICE_KEY=填写D调用B的独立随机密钥
D_SERVICE_COURSE_IDS=*
```

| 配置 | 含义 |
| --- | --- |
| DIAGNOSIS_AUTO_ENQUEUE | 默认 true；true/1/yes 启用正常提交及超时结算自动入队，其他值关闭。关闭时仍可手动 POST 创建任务 |
| DIAGNOSIS_URL | D 基础地址，默认 http://127.0.0.1:8002；worker 拼接 /internal/diagnosis-tasks |
| DIAGNOSIS_SERVICE_KEY | B→D 的接收凭证，D 新任务接收接口校验同一个值 |
| D_SERVICE_KEY | D→B 的数据读取凭证；D 读取任务 input 时使用 |
| D_SERVICE_COURSE_IDS | D 在 B 的课程白名单；* 允许全部，或英文逗号分隔实际课程 ID |
| DIAGNOSIS_TIMEOUT | 单次通知 HTTP 超时，默认 10，范围 1～300 秒 |
| DIAGNOSIS_MAX_ATTEMPTS | 每轮自动投递次数上限，默认 5，范围 1～100 |

两个方向的密钥必须至少 32 UTF-8 字节且互不相同，也不能与 C_SERVICE_KEY 相同。D_SERVICE_KEY 由 D 配置用于请求 B；DIAGNOSIS_SERVICE_KEY 由 D 配置用于验证 B 的任务通知。任何密钥都不交给浏览器。

worker 配置无效时直接报脱敏错误，不领取任务、不消耗次数。仅处理 D 课程白名单中的任务，其他任务保留 pending。B Web 可在 D 尚未配置时正常保存成绩和待处理任务。

3. D 完成接收端适配后，单独启动投递进程：

```sh
# 只处理一轮，适合调试或系统定时任务
python -m app.dispatch_diagnoses --limit 10

# 持续轮询，默认每 2 秒一轮；Ctrl+C 停止
python -m app.dispatch_diagnoses --watch --poll-interval 2 --limit 10
```

Web 启动命令仍为 `python -m app`。启动 Web 不会自动启动投递 worker；生产环境由进程管理器分别维护 Web 和 worker。每轮最多处理 1～1000 次 HTTP 投递，输出 delivered/pending/failed/stale 的本轮投递结果数量，不含扫描时发现并关闭的损坏/耗尽任务。

## 2. 何时创建任务

- 学生调用 `POST /attempts/{attempt_id}/submit`，首次完成评分时自动入队。
- 懒结算（访问到期测验）及 `python -m app.expire_attempts` 批量结算也入队。
- 评分与任务共用一个数据库事务；任一步写库失败都会回滚，不会报告成绩保存成功但丢失任务。
- 不在结算事务中访问 D。D 停机、处理慢、网络超时不会阻塞成绩提交。
- `attempt_id` 唯一约束配合作答行锁，保证一份测验只有一个通知任务；重复提交不会重复创建。
- 历史已完成测验不自动扫描入队，可通过下述 POST 补建。

提交和结果接口保留原响应结构，attempt_id 仍为返回的 data.id；查询任务使用独立 GET，不把 task_id 与 attempt_id 混用。

## 3. 学生/教师任务接口

| 方法 | 路径 | 权限 | 成功 HTTP |
| --- | --- | --- | --- |
| GET | `/attempts/{attempt_id}/diagnosis-task` | 本人学生 | 200 |
| POST | `/attempts/{attempt_id}/diagnosis-task` | 本人学生 | 202 |
| GET | `/teacher/attempts/{attempt_id}/diagnosis-task` | 所属课程教师 | 200 |
| POST | `/teacher/attempts/{attempt_id}/diagnosis-task` | 所属课程教师 | 202 |

使用正常登录 Token。POST 无请求体：没有任务则创建；pending/dispatching/delivered 返回原任务，不重复交付；failed 则恢复 pending，重置本轮 attempt_count 为 0，保留 task_id 和已冻结输入，以同一幂等键重试。状态 delivered 不能通过 POST 重新生成另一份诊断。

统一成功响应示例：

```json
{
  "code":0,"message":"ok",
  "data":{
    "id":"诊断任务ID","attempt_id":"测验作答ID","status":"pending",
    "attempt_count":0,"next_retry_at":1794800000,"last_error":null,
    "created_at":1794800000,"updated_at":1794800000,"delivered_at":null
  },
  "request_id":"请求追踪ID"
}
```

未结束测验返回 409；不存在或越权作答返回 404；GET 没有任务返回 404；角色不符 403，未登录 401，写库失败 503。查询到期测验会沿用现有懒结算。任务公开数据不返回标准答案、冻结输入、租约令牌、服务密钥或 D 原始响应。

## 4. 状态、重试和崩溃恢复

| 状态 | 含义 |
| --- | --- |
| pending | 等待首次交付，或等待下一次自动重试 |
| dispatching | worker 已提交输入快照和租约，正在通知 D |
| delivered | D 返回匹配的 accepted 回执，确认任务已接收 |
| failed | 不可重试错误、达到次数上限或输入损坏，需核对后手动重试 |

首次领取时生成并保存完整 `b-internal-1` 输入及摘要。冻结发生在首次交付准备时，不是学生提交时；之前的资料变化会体现在首次快照中。之后重试、worker 重启、手动重试都复用同一输入，不临时替换资料版本或评分。

领取顺序为作答行锁→任务行锁，使用 MySQL 8 的 SKIP LOCKED，避免与结算/手动重试的锁顺序冲突。先提交租约和冻结输入、关闭会话，再调用 D；HTTP 期间不持有数据库连接或行锁。租约为向上取整的 HTTP 超时加 30 秒。进程中断后，其他 worker 可在租约到期时重新领取，使用新 lease_token；旧 worker 的迟到回执不能覆盖新领取者的结果。

网络错误、超时、HTTP 408/425/429/5xx 自动重试，间隔为 5、10、20、40……秒，上限 300 秒。其他非 200/202 状态（含重定向、401/403/404/409/422）、非法 JSON、回执不匹配或超过 64 KiB，标为 failed。只保存 B 控制的错误描述，不保存 D 原始异常、正文、URL 或凭证。

最多次数默认 5。崩溃前一次领取也计数；租约耗尽且次数达到上限时转 failed，不能断言 D 一定没接收。先检查 D 的持久化接收记录，再用同一任务 ID 手动重试。此机制是至少一次交付；D 必须实现持久化幂等，不能宣称外部诊断计算严格恰好执行一次。

## 5. B→D 通知契约（D 需实现）

```http
POST /internal/diagnosis-tasks
Authorization: Bearer <DIAGNOSIS_SERVICE_KEY>
Idempotency-Key: <task_id>
X-Request-ID: <task_id>
Content-Type: application/json
```

通知 JSON：

```json
{
  "contract_version":"b-d-task-1",
  "task_id":"诊断任务ID",
  "attempt_id":"测验作答ID",
  "course_id":"demo-course-ds-teacher-2",
  "input_contract":"b-internal-1",
  "input_path":"/internal/diagnosis-tasks/诊断任务ID/input",
  "input_hash":"64位小写SHA256摘要"
}
```

D 处理要求：

1. 校验 B→D 密钥、契约和 Idempotency-Key；task_id 是 D 接收任务的唯一键。
2. **先持久化通知并保证后台工作可恢复，再返回 accepted**；相同 ID、相同 payload 重复通知返回同一接收回执，不能重复建立诊断任务。相同 ID 的不同 payload 返回 409。
3. 接收端快速返回，不在 HTTP 请求中等待整个诊断完成。
4. D 的工作进程使用自己配置的 B 基础地址，加相对 input_path，用 D_SERVICE_KEY 读取冻结输入；只允许约定的 B 路径，不能任意访问通知里的外部 URL。
5. 校验读取到的 task_id、attempt_id、course_id、契约和输入摘要，然后按新输入模型进行诊断、调用 C 取证。

成功接收返回 HTTP 202（重复接收可 200），**原始 JSON**，不套 B 的 code/data 包装：

```json
{"task_id":"诊断任务ID","attempt_id":"测验作答ID","status":"accepted"}
```

B 严格校验这三个字段、ID 相等及 status=accepted；不能返回空 202、仅 ok、整份旧 Report 或 completed 冒充接收回执。最终报告与完成回调需后续另行定义。

## 6. D→B 获取冻结输入

```http
GET /internal/diagnosis-tasks/{task_id}/input
Authorization: Bearer <D_SERVICE_KEY>
```

响应使用 B 统一包装，data 为：

```json
{
  "task_id":"诊断任务ID",
  "attempt_id":"测验作答ID",
  "input_hash":"64位小写SHA256摘要",
  "input":{
    "contract_version":"b-internal-1",
    "assessment_policy":"kp-accuracy-v1",
    "attempt_id":"测验作答ID"
  }
}
```

上例 input 只展示标识；实际包含完整题目快照、选项、最终答案、标准答案、评分统计、基准及当时可用资料目录，字段见 [内部数据接口与联调说明](内部数据接口与联调说明.md)。

摘要为对完整 input 使用 `json.dumps(..., ensure_ascii=False, sort_keys=True, separators=(',', ':'), allow_nan=False)` 后 UTF-8 编码计算 SHA-256。读取接口只允许 D，按作答实际所属课程校验白名单；未知/越课程任务 404，尚未准备输入 409。

`GET /internal/attempts/{attempt_id}/diagnosis-input` 仍可做临时导出，其资料目录会随当前资料变化；正式任务必须使用通知的 task input 路径。不能在同一次任务重试时改读实时导出。资料已更新或删除导致 C 不再提供某冻结版本时，D 应明确降级或报告版本不可用，不静默换成其他版本。需要使用新资料重新生成诊断，后续应新增独立任务版本，不能覆盖此任务的冻结输入。

## 7. 模型与迁移

DiagnosisTask / diagnosis_tasks 共十四列：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | VARCHAR(64) | PK，B 生成 UUID hex |
| attempt_id | VARCHAR(64) | NOT NULL、UNIQUE、FK→exam_attempts.id，RESTRICT |
| status | VARCHAR(20) | NOT NULL，默认 pending，CHECK 四种状态 |
| attempt_count | INTEGER | NOT NULL，默认 0，CHECK ≥0；本轮领取次数 |
| next_retry_at | BIGINT | NOT NULL，下一次可领取时间，Unix 秒 |
| lease_token | VARCHAR(64) | 可空，每次领取新的随机令牌 |
| lease_expires_at | BIGINT | 可空，领取失效时间 |
| input_snapshot | JSON | 可空，首次交付时冻结完整输入 |
| input_hash | VARCHAR(64) | 可空，冻结输入摘要 |
| receipt | JSON | 可空，校验后的 D accepted 回执 |
| last_error | TEXT | 可空，B 生成的脱敏错误 |
| created_at / updated_at | BIGINT | NOT NULL，创建/更新时间 |
| delivered_at | BIGINT | 可空，D 确认接收时间 |

dispatching 必须有租约，其他状态必须清空租约；input_snapshot 和 input_hash 同空或同非空；delivered 必须有 receipt 和 delivered_at。索引 `(status,next_retry_at)`、`(status,lease_expires_at)` 支持任务扫描。课程和学生信息通过 attempt 读取，不再重复存储。

## 8. 对 C 的接口是否足够

对于“课程资料同步→建立/更新/删除索引→给 D 返回检索证据”的基本资料供给，B 当前接口已提供必要信息：

| C 的需要 | B 已提供 |
| --- | --- |
| 知道有哪些课程 | GET /internal/courses，支持授权课程和分页 |
| 发现资料及变化 | 课程 resources 清单，含版本、状态和删除墓碑 |
| 获取可索引内容 | resource 详情的已提取正文、标题、来源、知识点 ID、摘要 |
| 确认处理状态 | PUT index-state，校验版本、摘要、幂等及旧回报 |

C 需要自行实现周期性拉取、分页、重试、持久化资料版本/删除墓碑、分块、索引及检索；根据 D 的可用资料目录限定课程和版本，并返回真实引用。当前 C 源码仍是 keyword_demo，尚无主动拉取 B、服务密钥适配及严格资料版本保护，不能把 B 接口可用等同于 C 已经接通或完成语义 RAG。

基本文本检索不要求 B 再增加接口；OCR、PDF 原始页码与切片偏移映射、图片/公式解析、严格增量变更流属于后续增强。当前 PDF/Word 由 B 提取正文，C 直接处理 text；现有清单需重复全量扫描，不能仅用秒级更新时间做永久水位。
